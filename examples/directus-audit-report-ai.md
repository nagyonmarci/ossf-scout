## 5. Findings

### F-001 · SSRF via server-side fetch of user-supplied URLs
**OWASP:** A10:2021 · **CWE:** CWE-918 · **Severity:** CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:L/I:N/A:N → **4.3 Medium**

**Description.** Several server paths issue outbound HTTP requests to URLs that originate from
client input:
- `api/src/services/files.ts:285` — `axios.get<Readable>(encodeURL(importURL), …)` (the "import file from URL" feature).
- `api/src/services/mcp-oauth/cimd.ts:277` — `axios.get(clientId, requestConfig)` (fetches an OAuth client-metadata document from a client-supplied identifier).
- `api/src/permissions/utils/fetch-dynamic-variable-data.ts:118` — `fetch(fields)`.

**Root cause.** These are intentional outbound-fetch features, but the destination is influenced by
the caller. Without an egress allowlist / IP-range denylist, an authenticated user can point the
server at internal addresses (link-local `169.254.169.254`, RFC-1918 ranges, `localhost`).

**Impact chain.** Authenticated user (with file-create or OAuth-registration permission) → submits an
internal URL → Directus fetches it server-side → response/metadata may be reflected → limited
disclosure of internal service responses or cloud metadata. Rated `C:L` (no integrity/availability
impact and authentication/permission is required, hence `PR:L`).

**Fix.** Resolve and validate the target before fetching — reject non-public IP ranges:
```ts
import { lookup } from 'node:dns/promises';
import ipaddr from 'ipaddr.js';
async function assertPublic(url: string) {
  const { hostname } = new URL(url);
  const { address } = await lookup(hostname);
  const range = ipaddr.parse(address).range();
  if (['private','loopback','linkLocal','uniqueLocal','reserved'].includes(range))
    throw new Error('blocked: non-public address');
}
```
Apply before each `axios.get`/`fetch` above; keep the check on the resolved IP to defeat DNS rebinding.

**Verification.**
```bash
rg -n "axios.get\(.*importURL|axios.get\(clientId|fetch\(fields\)" api/src
# After fix: importing http://169.254.169.254/latest/meta-data/ must be rejected, not fetched.
```

### F-002 · Unpinned GitHub Actions (third-party, mutable tags)
**OWASP:** A08:2021 · **CWE:** CWE-1357 · **Severity:** CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:L/I:L/A:N → **4.8 Medium**

**Description.** 50+ workflow steps reference actions by mutable tag rather than a commit SHA. Highest
concern are **third-party** actions:
- `tj-actions/changed-files@v47` — `.github/workflows/changeset-check.yml:32`, `.github/workflows/check.yml:32,56,75`
- `anthropics/claude-code-action@v1` — `.github/workflows/claude.yml:35`, `.github/workflows/claude-code-review.yml:23`
- `peter-evans/dockerhub-description@v4`, `marocchino/sticky-pull-request-comment@v2`, `madhead/semver-utils@v4`, `dessant/lock-threads@v6`, `sigstore/cosign-installer@v3`.

First-party actions (`actions/checkout@v6`, `github/codeql-action/*@v4`) are also tag-pinned.

**Root cause.** Tags are mutable; if a third-party action's tag is repointed (maintainer compromise),
the new code runs in CI with that workflow's token. `changeset-check.yml` grants `pull-requests: write`
and runs `tj-actions/changed-files` on the `pull_request` event.

**Severity calibration.** Per the supply-chain rubric this is a **hardening gap (Medium)**, not
Critical: `changeset-check.yml` uses `pull_request` (not `pull_request_target`), so fork PRs get a
read-only token and the `pull-requests: write` grant does not apply to forks. No demonstrated secret
exfiltration path was captured. *(Triggers/permissions for `claude.yml` were not captured — if it runs
on `issue_comment`/`pull_request_target` with write scope it should be re-rated High.)*

**Fix.** Pin every `uses:` to a full commit SHA and let Dependabot bump them:
```yaml
# resolve the SHA for the tag you trust, then pin it:
#   git ls-remote https://github.com/tj-actions/changed-files refs/tags/v47
- uses: tj-actions/changed-files@<RESOLVED_SHA>   # v47  (SHA not captured — resolve before committing)
```
Enable `dependabot` `package-ecosystem: github-actions`.

**Verification.**
```bash
rg -n "uses: .*@v[0-9]" .github/workflows   # must return nothing once fully pinned
```

### F-003 · Production Docker base image not digest-pinned
**OWASP:** A08:2021 · **CWE:** CWE-1357 · **Severity:** CVSS:3.1/AV:N/AC:H/PR:N/UI:R/S:U/C:L/I:L/A:N → **3.9 Low**

**Description.** `Dockerfile` builds on a floating tag — `FROM node:${NODE_VERSION}-alpine`
(`NODE_VERSION=22`) for both `builder` and `runtime` stages — and installs `corepack@latest` /
`pm2@5` globally. Floating tags make builds non-reproducible and allow a silently different base image.

**Positive notes (evidence):** the runtime stage drops to `USER node` (non-root) and uses a multi-stage
build — both good practices.

**Fix.**
```dockerfile
FROM node:22-alpine@sha256:<digest> AS builder   # pin by manifest digest
# ...
RUN npm install --global pm2@5.4.3 corepack@0.32.0   # pin exact versions
```

**Verification.**
```bash
rg -n "^FROM .*:(?!.*@sha256)" Dockerfile   # any match = unpinned base image
```

### F-004 · `X-Powered-By: Directus` header explicitly set
**OWASP:** A05:2021 · **CWE:** CWE-200 · **Severity:** CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:N → **0.0 Informational**

**Description.** `api/src/app.ts:152` correctly calls `app.disable('x-powered-by')`, but `api/src/app.ts:237`
then sets `res.setHeader('X-Powered-By', 'Directus')`, re-advertising the software. This is fingerprinting
information only — no direct security impact, hence Informational.

**Fix.** Remove the explicit header (or gate it behind a debug flag).

**Verification.**
```bash
curl -sI http://localhost:8055/server/ping | grep -i x-powered-by   # expect no output
```

### F-005 · Sandboxed `eval` in the `exec` flow operation
**OWASP:** A03:2021 · **CWE:** CWE-95 · **Severity:** CVSS:3.1/AV:N/AC:H/PR:H/UI:N/S:U/C:L/I:L/A:L → **0.0 Informational (by design)**

**Description.** `api/src/operations/exec/index.ts:49` runs `context.eval(code, { timeout: scriptTimeoutMs })`.
The `context` is an isolated-vm sandbox and the executed `code` comes from a Flow's "Run Script"
operation, which only an **administrator** can author. This is a documented platform feature, not an
injection bug — listed for transparency.

**Recommendation.** Keep flow-creation restricted to trusted admin roles; document the sandbox boundary
and timeout in the security docs.
